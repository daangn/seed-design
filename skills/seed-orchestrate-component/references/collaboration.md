# 협업 절차

## 1. 범위와 공통 계약

조율자는 현재 요청에 필요한 항목만 작업 메모 한 곳에 적는다. 하네스에 공유 작업·산출물 기능이 있으면 그것을 쓰고, 없으면 작업용 파일 경로를 전달한다. 영구 DB, 세션 로그 체계, 메시징 서버는 만들지 않는다.

- 사용자 결과: 원래 참조 시나리오·화면, 조건·입력·기대 결과, 의도적인 플랫폼 차이
- 파일 소유권: 역할별 실제 담당, 쓰기 허용 경로, 공유 파일의 단일 작성자
- 공동 계약: 공개 API, prop과 slot의 렌더링 책임, provider 범위, 상태·표시 수명, 토큰·variant 대응
- 의존 관계: 먼저 필요한 결정·원천·생성물과 이를 소비하는 담당
- 실행 소유권: 생성·통합 빌드 담당, 검증 종류별 실행자, 조율자의 최종 승인, 서버·기기·공유 자원 조작 담당
- 검증 조건: 시나리오별 필수·선택 환경, 기대 결과, 쓸 수 없는 환경의 처리
- 참조 동작: [행동별 원천 추적](../../seed-component/references/implementation-steps.md#행동별-원천-추적)의 원천·대상 책임·미확인 연결
- 기본 장면: 가장 먼저 실행할 공개 소비 경로, 통과 전에는 넓히지 않을 의존 작업

계약은 변경을 만드는 쪽과 쓰는 쪽(Rootage↔Recipe, Recipe↔플랫폼, 플랫폼↔Registry)만 확인한다. 전원 승인을 기다리지 않고, 해결되지 않은 쟁점과 관계없는 작업은 진행한다. 기존 생성 변수·API를 재사용하는 경계에는 설계 회의를 요구하지 않는다. 새 합의가 필요한 경계만 기록한다.

## 2. 위임

다른 담당이나 조율자가 읽은 대화·Skill·파일이 자동으로 전달된다고 가정하지 않는다. 각 담당에게 다음을 모두 전달한다.

```text
목표와 기대 사용자 결과
담당 역할과 정확한 쓰기 범위, 수정 금지 범위
읽을 원천·참조·기존 Skill
관련 생산자·소비자와 합의한 계약
먼저 필요한 결과, 독립적으로 진행할 부분
실행을 맡은 검사와 다른 담당에게 넘길 검사
완료 조건과 반환할 근거
```

역할 이름과 실제 에이전트 ID를 구분한다. 생성 결과에서 확인한 ID를 관련 담당에게 알린다. 담당은 받은 범위 안에서만 행동하고, 추가 담당이 필요하면 범위와 이유를 조율자에게 보낸다.

## 3. 의견 교환

다음 변화가 있을 때만, 영향받는 담당에게만 알린다.

- 공개 prop·slot·provider 구조 또는 렌더링 소유권 변경
- 상태·측정·모션 수명 또는 토큰·variant 의미 변경
- 배포 방식, 생성·빌드 순서, 실제 소비 경로 변경
- 원래 기대 결과를 충족하지 못하는 플랫폼 제약이나 재현 실패

메시지에는 쟁점, 원천 근거, 제안, 영향받는 소비처, 상대가 결정할 일을 담는다. 단순 진행 상황은 작업 상태로 남기고 전원에게 반복 전송하지 않는다.

예: ScrollArea 여백을 바꾸면 Recipe 담당은 적용 slot을 전달하고, 통합 담당은 실제 wrapper가 그 요소를 렌더링하는지 확인한다. 확인되지 않았으면 CSS 생성만으로 작업을 끝내지 않는다. 검증 담당은 최신 bundle의 요소와 computed style을 확인한다.

- 직접 통신이 없으면 조율자가 원문을 상대에게 전달하고 답변을 원래 담당에게 돌려준다. 요약하면서 반대 의견이나 불확실성을 지우지 않는다.
- 메시지 전달 성공은 동의가 아니다. 계약을 소비하기 전에 답변을 확인한다.
- 의견이 충돌하면 조율자가 원천과 사용자 결과를 기준으로 결정한다. 최소 실험으로 풀 수 있으면 실행 소유자를 정한다. 범위·권한을 바꾸는 미정 사항만 사용자에게 묻는다.

## 3-1. 계약 검토와 결과 승인

변경되는 공개 경계나 미확인 가정에만 적용한다. 확정된 기존 동작과 원천은 그대로 전달하고, 형식적인 착수 제안이나 전원 승인을 요구하지 않는다.

1. 제안자는 `[PROPOSE]`에 바꿀 행동·경계, 참조 원천, 가정, 영향받는 소비처를 담는다.
2. 영향받는 담당은 근거를 확인해 `[ACK]`, 또는 불일치·영향·대안을 담은 `[CONFLICT]`로 답한다. 기다리는 동안 그 결정과 무관한 작업은 진행한다.
3. 바뀐 경계를 소비하는 담당은 실제 원천을 읽고 `[REVIEW_PASS]`, 또는 문제·근거·수정 담당을 담은 `[REVIEW_REQUEST_CHANGES]`를 반환한다. 같은 파일 작성자의 자기 리뷰로 대신하지 않는다.

- 합의되지 않은 경계를 확정 입력으로 소비하지 않는다. 검토가 막히면 차단 사유를 반환하거나 조율자가 검토 담당을 다시 배정한다.
- 모든 작업자가 서로의 완료를 기다리는 순환 의존을 만들지 않는다. 직접 통신이 없으면 조율자가 원문과 답변을 중계한다.

계약 리뷰와 사용자 결과 승인은 별개다.

- `REVIEW_PASS`는 공개 API·slot·provider·소비 방식이 일치한다는 판정일 뿐이다. 화면이나 상호작용이 올바르다는 보장이 아니다.
- 검증자는 구현자의 완료 요약 대신 원래 참조 화면·시나리오·승인 조건을 받아 실제 결과를 대조하고, [관찰 가능한 결과 판정](../../seed-component/references/verification-checklist.md#관찰-가능한-결과-판정)에 따라 환경별 기대·실제 결과와 증거를 반환한다.
- 조율자는 그 증거를 승인 조건과 대조한다. 보고가 부족하거나 충돌하면 직접 확인하거나 재검증을 배정하고, 근거 없는 통과는 승인하지 않는다.
- `READY`, `worker_done` 같은 종료 신호는 작업 인계에만 쓴다. 미검토 경계·실패·차단은 종료 결과에도 남기고 전체 완료 판정과 구분한다.

## 검증 분담과 자원

조율자는 원래 승인 조건과 반환된 증거를 대조해 최종 승인한다. 검증을 한 명에게 직렬로 모으지 않고, 검증마다 작업자를 새로 만들지도 않는다. 원천을 수정하는 동안에는 그 원천의 최종 검증을 시작하지 않는다.

안정된 변경본에서 입력·생성물·충돌 자원이 독립한 다음 검사는 각각 지정 실행자에게 함께 배정한다.

- package 타입·회귀 → 선행 입력: 안정된 package 원천, 필요한 생성물
- Registry·문서·예제 소비 연결 → 선행 입력: 안정된 소비 경로, 소비할 생성물의 생성 완료
- 런타임 화면·상호작용 → 선행 입력: 안정된 실행 bundle, 시나리오, 전용 조작 자원

생성물을 소비하는 검사는 그 생성물의 완료만 기다린다. 가벼운 독립 검사는 무거운 검사가 끝나기를 기다리지 않는다.

### Lynx native 기본 장면

- Lynx native 기본 장면은 [`검증 런북`](../../seed-verify-lynx-component/references/verification.md)의 `examples/lynx-spa` 문서 예제로 확인한다.
- 전체 docs 빌드나 정적 bundle 서빙은 MDX 페이지·`LynxComponentExample` host·코드 탭·QR·Web preview·docs pipeline 자체를 바꾼 경우에만, 그 문서 변경 부분을 확인하려고 추가한다.
- 온라인 검증을 배정하기 전에 실행자가 [session 소유권과 Card 수명](../../seed-verify-lynx-component/references/concurrency/session-ownership.md)을 읽게 한다.
- 공통 작업 메모에 생성 요청 client, host 식별 근거, 공유 잠금 경로, 소유자를 적는다. Card 생성 뒤에는 점유한 client/session 쌍과 bundle URL을 더한다.
- 다른 실행자는 그 쌍에 자기 bundle을 로드하거나 같은 URL의 Card를 다시 점유하지 않는다. 같은 PlayLynx client의 다음 실행자는 이전 Card 제거 확인과 잠금 해제가 끝난 뒤 시작한다. 다른 client라도 host·기기·overlay·캡처 자원이 독립적일 때만 함께 실행한다.

### 공유 자원

- 전역 overlay·호스트 창·기기·캡처 대상·공유 산출물마다 조작 소유자를 한 명 둔다.
- 호스트 격리는 프로세스·창 또는 기기 식별자와 overlay·캡처 자원 공유 여부로 확인한다. session ID·포트·worktree만 다른 것은 격리 근거가 아니다.
- 변경 없는 서빙 출력에는 읽기 전용 소비자 여럿이 붙을 수 있다. 서버 시작·재시작·중지는 서버 수명 소유자가, 생성물 갱신은 그 출력 소유자가 하며, 소비 중인 변경본을 바꾸지 않는다.
- CPU·메모리를 많이 쓰는 생성·빌드·타입 분석·대규모 회귀 검사는 처음엔 하나만 돌리고 여유를 확인한 뒤 늘린다. 자원 경합을 테스트 timeout 증가로 숨기지 않는다.

### 검증 인계

인계는 한 줄로 남긴다: `변경본 식별자 → 실행 명령/시나리오 → 판정과 기대·실제 결과 → 증거 → 실패 원천·영향 범위`. Lynx native는 SPA 예제 ID, query를 포함한 bundle URL, 변경본과 환경 근거를 더한다. 실패나 후속 수정 뒤에는 실패한 검사와 영향받는 검사만 다시 실행한다.

## 4. 구현과 통합 순서

1. 검증 실행 담당은 구현 전에 원래 참조·승인 조건·필수 환경·재현 경로를 확인한다. 참조 동작의 미확인 연결은 해당 구현의 선행 조사로 둔다. 환경 차단이 있어도 독립적인 승인 범위는 진행한다.
2. [기본 장면 우선 검증](../../seed-component/references/implementation-steps.md#기본-장면-우선-검증)에 따라 필요한 원천과 공개 소비 경로부터 연결한다. 새 Rootage 변수처럼 필요한 생성물은 지정 담당이 만든 뒤 소비한다.
3. 계약과 입력이 준비된 독립 쓰기 범위는 함께 실행한다. 동시 쓰기 구간에서는 각 담당이 포맷터·생성·빌드·린트·테스트를 실행하지 않는다. 기본 장면의 원천·소비 경로를 안정시킨 검증 구간을 먼저 확보하고, 전체 구현이 끝날 때까지 실행을 미루지 않는다.
4. 통합 담당이 그 구간의 package export·Registry wrapper·vendored 소비처와 생성·빌드를 연결한다. 최신 원천이 실제 bundle에 들어갔는지 확인한 뒤 필요한 생성물만 검증 실행자에게 넘긴다. 커밋이 없으면 통합 차수와 변경 경로로 변경본을 식별한다.
5. 기본 장면이 통과한 뒤에 그 동작에 의존하는 변형·예제를 넓힌다. 실패는 원천 담당이 고치고, 통합 담당이 필요한 재생성을 한 뒤 그 장면의 검증 실행자가 다시 확인한다. 차단된 의존 작업과 진행 가능한 독립 작업을 구분한다.
6. 나머지 요청 범위를 통합한 뒤 필수 시나리오·환경을 모두 검증한다. 후속 변경이 이미 통과한 결과에 영향을 주면 그 항목을 `미확인`으로 되돌려 재검증한다. 기본 장면 통과로 최종 검증을 생략하지 않는다.

생성·빌드를 늦추는 것은 공유 출력 충돌을 피하려는 것이지 검사를 생략하는 근거가 아니다. 상위 지침이 요구하는 검사는 유지한다. 필요한 테스트는 원천 담당이 기존 패턴대로 고치고, 새 테스트 체계나 검증용 가짜 소비자는 만들지 않는다.

## 5. 실행 대상 인계

bundle·서버·기기가 관련된 작업에서만 다음을 인계한다.

- 현재 worktree와 통합 변경본, 실제로 수행한 package·예제 빌드
- 문서·시나리오 ID, entry와 manifest의 실제 bundle 경로. Lynx native는 SPA 예제 ID와 query를 포함한 전체 bundle URL
- 서빙 루트·실제 주소·서버 소유자, 사용하는 client·session
- 그 변경본에서 수집한 화면·DOM·console·측정 증거

명령 종료나 포트 응답만으로 올바른 worktree의 bundle이 로드됐다고 보지 않는다 → 해시 유무와 URL을 현재 manifest에서 확인하고, 실행 중인 서버와 기기 session이 그 대상을 소비하는지 확인한다. Lynx native는 query를 포함한 bundle URL과 변경본·환경 근거도 대조한다. 세부 명령은 [검증 런북](../../seed-verify-lynx-component/references/verification.md)을 따른다.

기존 사용자 세션은 임의로 종료하지 않는다. 다른 담당이 계속 쓸 자원은 변경본·상태와 함께 명시적으로 인계한다. 자원 소유와 병렬 실행은 [검증 분담과 자원](#검증-분담과-자원)을 따른다.

## 6. 변경과 완료 판정

새 사용자 요구나 계약 변경이 생기면 조율자가 해당 항목과 필수 환경을 갱신하고 관련 담당에게 전달한다. 이미 통과한 검증도 결과에 영향을 주는 후속 수정이 있으면 그 항목만 `미확인`으로 되돌린다.

검증 실행 담당은 시나리오·환경별로 `통과`, `실패`, `환경 차단`, `미확인` 중 하나와 기대/실제 결과·증거를 반환한다. 작성자는 자기 작업 종료를 전체 완료로 선언하지 않는다.

조율자는 세 가지를 따로 판정한다.

- 구현 반영: 원천과 필요한 소비물이 갱신됐는가
- 기능 확인: 필수 환경에서 요청한 시각·상호작용 결과를 직접 확인했는가
- 성능 확인: 성능 개선을 주장한다면 목표 기기·시나리오의 측정 근거가 있는가

전체 판정:

- 필수 항목이 모두 `통과` → 전체 완료
- 필수 항목에 `실패` → 전체 실패
- 필수 항목에 `환경 차단`·`미확인` → 전체 미완료
- 선택 환경의 제한 → 완료를 막지 않지만 보고에 남긴다. 예: Android 최적화 옵션 검토는 코드·문서 근거로 마칠 수 있지만, iOS에서 목록 열기·스크롤이 성공한 것을 Android 첫 표시 성능 개선으로 보고하지 않는다.

검증자가 지적한 차이는 증거로 해결한다. 테스트나 기대 결과를 구현에 맞춰 낮추거나 미지원으로 재분류해 통과시키지 않는다. 요구사항·지원 범위를 실제로 바꾸는 경우에는 근거와 사용자 결정을 먼저 반영한다.
