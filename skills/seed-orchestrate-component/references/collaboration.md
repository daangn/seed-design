# 협업 절차

## 1. 범위와 공통 계약

조율자가 현재 요청에서 필요한 항목만 작업 메모 한 곳에 기록한다. 하네스의 공유 작업·산출물 기능이 있으면 사용하고, 없으면 작업용 파일 경로를 전달한다. 별도 영구 DB, 세션 로그 체계나 메시징 서버를 만들지 않는다.

| 항목 | 기록할 내용 |
| --- | --- |
| 사용자 결과 | 원래 참조 시나리오·화면, 조건·입력·기대 결과, 의도적인 플랫폼 차이 |
| 파일 소유권 | 역할별 실제 담당, 쓰기 허용 경로, 공유 파일의 단일 작성자 |
| 공동 계약 | 공개 API, prop과 slot의 렌더링 책임, provider 범위, 상태·표시 수명, 토큰·variant 대응 |
| 의존 관계 | 먼저 필요한 결정·원천·생성물과 이를 소비하는 담당 |
| 실행 소유권 | 생성·통합 빌드 담당, 최종 검사 담당, 서버·기기 session 담당 |
| 검증 조건 | 시나리오별 필수·선택 환경, 기대 결과, 사용할 수 없는 환경의 처리 |
| 참조 동작 | [행동별 원천 추적](../../seed-create-component/references/implementation-steps.md#행동별-원천-추적)의 원천·대상 책임·미확인 연결 |
| 기본 장면 | 가장 먼저 실행할 공개 소비 경로, 통과 전 확장하지 않을 의존 작업 |

Rootage와 Recipe, Recipe와 플랫폼, 플랫폼과 Registry처럼 변경을 만드는 쪽과 사용하는 쪽이 해당 계약을 확인한다. 모든 담당의 전원 승인을 기다리지 않는다. 해결되지 않은 쟁점과 관계없는 작업은 진행한다.

기존 생성 변수·API를 재사용하는데 새로운 설계 회의를 요구하지 않는다. 새 합의가 필요한 경계만 기록한다.

## 2. 위임

각 담당에게 다음을 전달한다. 다른 담당이나 조율자의 대화·스킬·파일 읽기가 자동으로 상속된다고 가정하지 않는다.

```text
목표와 기대 사용자 결과
담당 역할과 정확한 쓰기 범위, 수정 금지 범위
읽을 원천·참조·기존 스킬
관련 생산자·소비자와 합의한 계약
먼저 필요한 결과, 독립적으로 진행할 부분
실행을 맡은 검사와 다른 담당에게 넘길 검사
완료 조건과 반환할 근거
```

역할 이름과 실제 에이전트 ID를 구분한다. 생성 결과에서 확인한 ID를 관련 담당에게 알려준다. 각 담당은 이 작업 범위 안에서만 행동하고, 추가 담당이 필요하면 조율자에게 범위와 이유를 전달한다.

## 3. 의견 교환

다음 변화가 있을 때 관련 담당에게만 알린다.

- 공개 prop·slot·provider 구조 또는 렌더링 소유권 변경
- 상태·측정·모션 수명 또는 토큰·variant 의미 변경
- 배포 방식, 생성·빌드 순서, 실제 소비 경로 변경
- 원래 기대 결과를 충족하지 못하는 플랫폼 제약이나 재현 실패 발견

메시지에는 쟁점, 원천 근거, 제안, 영향받는 소비처, 상대가 결정할 일을 담는다. 단순 진행 상황은 작업 상태로 남기고 같은 내용을 전원에게 반복 전송하지 않는다.

예를 들어 ScrollArea 여백을 바꿀 때 Recipe 담당은 적용 slot을 전달하고, 통합 담당은 실제 wrapper가 그 요소를 렌더링하는지 확인한다. 확인되지 않았다면 CSS 생성만으로 작업을 끝내지 않는다. 검증 담당은 최신 번들의 요소와 computed style을 확인한다.

직접 통신이 없으면 조율자가 같은 내용을 상대 담당에게 전달하고 답변을 원래 담당에게 돌려준다. 조율자의 요약으로 반대 의견이나 불확실성을 지우지 않는다. 메시지 전달 성공은 상대의 동의가 아니므로 계약을 소비하기 전에 답변을 확인한다.

의견이 충돌하면 조율자가 원천과 사용자 결과를 기준으로 결정한다. 필요한 최소 실험으로 해소할 수 있으면 그 실행 소유자를 정한다. 같은 논쟁을 반복하지 않고, 범위·권한을 바꾸는 미정 사항만 사용자에게 묻는다.

## 3-1. 계약 검토와 결과 승인

변경되는 공개 경계나 미확인 가정에만 다음 교환을 적용한다. 확정된 기존 동작과 원천은 그대로 전달하고, 모든 담당에게 형식적인 착수 제안·전원 승인을 요구하지 않는다.

1. 제안자는 `[PROPOSE]`에 변경할 행동·경계, 참조 원천, 가정과 영향받는 소비처를 담는다.
2. 영향받는 담당은 근거를 확인해 `[ACK]` 또는 불일치·영향·대안을 포함한 `[CONFLICT]`로 답한다. 응답을 기다리는 동안 해당 결정과 무관한 작업은 진행한다.
3. 변경된 경계를 소비하는 담당은 실제 원천을 읽고 `[REVIEW_PASS]` 또는 문제·근거·수정 담당을 포함한 `[REVIEW_REQUEST_CHANGES]`를 반환한다. 같은 파일의 자기 리뷰로 대체하지 않는다.

미합의 경계를 확정된 입력으로 소비하지 않는다. 해당 인계의 검토가 막히면 차단 사유를 반환하거나 조율자가 검토 담당을 재배정한다. 모든 작업자가 서로의 완료를 기다리는 순환 의존성을 만들지 않는다. 직접 통신이 없으면 조율자가 원문과 답변을 중계한다.

계약 리뷰와 사용자 결과 승인은 별개다.

- `REVIEW_PASS`는 공개 API·slot·provider·소비 방식의 일치에 대한 판정이다. 올바른 화면이나 상호작용을 보장하지 않는다.
- 검증자는 구현자의 완료 요약 대신 원래 참조 화면·시나리오·승인 조건을 받아 실제 결과를 대조한다. [관찰 가능한 결과 판정](../../seed-create-component/references/verification-checklist.md#관찰-가능한-결과-판정)에 따라 환경별 기대·실제 결과와 증거를 반환한다.
- 조율자는 이 증거를 승인 조건과 대조한다. 작업자 보고가 부족하거나 충돌하면 직접 확인하거나 재검증을 배정한다. 근거가 없는 통과를 그대로 승인하지 않는다.

`READY`와 `worker_done` 같은 종료 신호는 작업 인계에만 사용한다. 미검토 경계·실패·차단은 종료 결과에도 남기고, 전체 완료 판정과 구분한다.

## 4. 구현과 통합 순서

1. 검증 담당은 구현 전에 원래 참조·승인 조건·필수 환경과 재현 경로를 확인한다. 참조 동작의 미확인 연결은 해당 구현의 선행 조사로 두며, 환경 차단이 있어도 독립적인 승인 범위는 진행한다.
2. [기본 장면 우선 검증](../../seed-create-component/references/implementation-steps.md#기본-장면-우선-검증)에 따라 필요한 원천과 공개 소비 경로부터 연결한다. 새 Rootage 변수처럼 필요한 생성물은 지정 담당이 만든 뒤 소비한다.
3. 계약과 입력이 준비된 독립 쓰기 범위는 함께 실행한다. 동시 쓰기 구간에서는 각 담당이 포맷터·생성·빌드·린트·테스트를 실행하지 않는다. 기본 장면의 원천·소비 경로를 안정시킨 검증 구간을 먼저 확보하고, 전체 구현 종료까지 실행을 미루지 않는다.
4. 통합 담당은 해당 구간의 package export·Registry wrapper·vendored 소비처와 생성·빌드를 연결한다. 최신 원천이 실제 번들에 포함됐는지 확인한 뒤 검증 담당에게 넘긴다. 커밋이 없으면 통합 차수와 변경 경로로 변경본을 식별한다.
5. 기본 장면이 통과해야 그 동작에 의존하는 변형·예제 구현을 넓힌다. 실패는 원천 담당이 수정하고, 통합 담당의 필요한 재생성 후 검증자가 해당 장면을 다시 확인한다. 차단된 의존 작업과 진행 가능한 독립 작업을 구분한다.
6. 나머지 요청 범위를 통합한 뒤 필수 시나리오·환경을 모두 검증한다. 후속 변경이 이미 통과한 결과에 영향을 주면 해당 항목을 `미확인`으로 되돌려 재검증한다. 기본 장면의 성공으로 최종 검증을 생략하지 않는다.

상위 지침이 요구하는 검사는 유지한다. 생성·빌드를 늦추는 것은 공유 출력 충돌을 피하기 위한 것이며 검사를 생략하는 근거가 아니다. 필요한 테스트는 원천 담당이 기존 패턴에 맞춰 수정하고, 새 테스트 체계나 검증용 가짜 소비자를 만들지 않는다.

## 5. 실행 대상 인계

번들·서버·기기가 관련된 작업에서만 다음을 인계한다.

- 현재 worktree와 통합 변경본, 실제 수행한 package·예제 빌드
- 문서·시나리오 ID, entry와 manifest의 실제 bundle 경로
- 서빙 루트·실제 주소와 서버 소유자, 사용하는 client·session
- 해당 변경본에서 수집한 화면·DOM·console·측정 증거

명령 종료나 포트 응답만으로 올바른 worktree의 번들이 로드됐다고 보지 않는다. 해시 유무와 URL은 현재 manifest에서 확인하고, 실행 중인 서버와 기기 session이 그 대상을 소비하는지 확인한다. 세부 명령은 기존 검증 런북을 사용한다.

서버와 기기 session의 조작 책임은 검증 담당 한 명에게 둔다. 기존 사용자 세션은 임의 종료하지 않는다. 다른 담당이 계속 사용할 자원은 소유권을 명시적으로 넘기고, 그 외에는 실행 소유자가 기존 검증 지침에 따라 정리한다.

## 6. 변경과 완료 판정

새 사용자 요구나 계약 변경이 생기면 조율자가 해당 항목과 필수 환경을 갱신하고 관련 담당에게 전달한다. 이미 통과한 검증도 결과에 영향을 주는 후속 수정이 있으면 그 항목만 `미확인`으로 돌린다.

검증 담당은 시나리오·환경별로 `통과`, `실패`, `환경 차단`, `미확인`과 기대/실제 결과·증거를 반환한다. 작성자는 자신의 작업 종료를 전체 완료로 선언하지 않는다.

조율자는 다음을 구분한다.

- 구현 반영: 원천과 필요한 소비물이 갱신됐는가?
- 기능 확인: 필수 환경에서 요청한 시각·상호작용 결과를 직접 확인했는가?
- 성능 확인: 성능 개선을 주장한다면 목표 기기·시나리오의 측정 근거가 있는가?

필수 항목이 모두 통과해야 전체 완료다. 필수 실패는 전체 실패, 필수 환경 차단·미확인은 전체 미완료로 보고한다. 선택 환경의 제한은 완료를 막지 않지만 숨기지 않는다. 예를 들어 Android 최적화 옵션 검토는 코드·문서 근거로 마칠 수 있으나, iOS의 목록 열기·스크롤 성공을 Android 첫 표시 성능 개선으로 보고할 수는 없다.

검증자가 지적한 차이는 증거에 기반해 해결한다. 테스트나 기대 결과를 구현에 맞춰 낮추거나 미지원으로 재분류해 통과시키지 않는다. 실제 요구사항·지원 범위 변경이라면 그 근거와 사용자 결정을 먼저 반영한다.
