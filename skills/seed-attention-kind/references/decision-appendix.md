# 대화의 참고 근거

계획·설계 제안·리뷰·결과 보고에서 실제 판단에 사용한 근거를 사용자가 추적할 수 있게 한다.

## 적용과 형식

- 답변 끝에 `**참고 근거**`를 두고 실제 사용한 lesson·decision·AGENTS·Skill·코드·검증 결과·외부 원문을 연결한다. 각 항목은 `종류 · [제목](링크) — 이번 판단에 적용한 조건과 영향`으로 한 줄씩 쓴다.
- 로컬 파일은 클릭 가능한 절대 경로를 쓰고, 확인한 PR·원문은 실제 URL을 쓴다. 여러 환경에 공유하는 문서는 저장소 링크를 쓴다. 확인하지 않은 링크·줄 번호·출처를 만들지 않는다.
- 보통 핵심 근거 1–3개를 고른다. 중요한 조건·충돌·예외의 근거는 개수 때문에 생략하지 않는다. 단순 확인·인사·같은 판단의 반복에는 같은 목록을 붙이지 않는다.
- 진행 중 새 판단이나 방향 변경을 설명할 때는 그 판단에 사용한 근거를 함께 연결한다. 중간 메시지에 링크를 뒀어도 최종 답변은 필요한 근거를 자체적으로 포함한다.

## 근거의 경계

- 실제 적용한 자료만 근거로 제시한다. 검색 결과·frontmatter만 조회했다면 본문을 적용했다고 말하지 않는다. 참고했지만 적용하지 않은 결정은 충돌·제외 이유가 판단에 중요할 때 구분해 적는다.
- decision은 현재 상태와 적용 조건을 확인한다. `proposed`는 제안으로, 대체·폐기된 결정은 이력으로 표시한다. lesson의 경험을 합의된 정책처럼 인용하지 않는다.
- 근거의 내용과 에이전트의 해석·제안, 사용자가 이번 대화에서 확정한 선택을 구분한다. 파일 출처가 없으면 `이번 사용자 요청` 또는 `새 제안`으로 밝히고 출처를 지어내지 않는다.
- 코드·설정이 있다는 사실은 실행 증거가 아니다. 검증을 인용하면 실제 명령·결과·미검증 범위를 본문에 밝힌다. 기록에는 실제 파일·검사 경로를 연결하되 자동 호출·강제를 확인했다고 확대하지 않는다.
- 위험·실패·승인이 필요한 사항은 본문에 둔다. appendix는 그 설명을 확인할 링크이며, 중요한 조건을 뒤로 숨기는 곳이 아니다. 비밀·개인 환경 정보는 인용하지 않는다.

## 예시

본문: 관련 확정 결정의 적용 조건을 계획에서 확인하고, 경험에서 확인한 교훈과 선택의 이유를 분리해 기록한다.

참고 근거에는 다음처럼 연결한다. 실제 답변에서는 사용 환경의 절대 경로 또는 확인한 저장소 URL을 쓴다.

- Decision · [선택의 이유는 lesson과 분리해 경로별로 조회한다](../../../.agents/decisions/entries/scoped-decision-records.md) — 확정된 기록 구조와 계획 조회 범위를 적용했다.
- 지침 · [결정 기록 관리 규칙](../../../.agents/decisions/AGENTS.md) — 제안을 확정된 정책으로 취급하지 않고 적용 조건·확정 근거를 남긴다.
