# PR의 기록과 최종 변경 대조

PR을 제출·갱신하거나 머지 직전 확인을 할 때, 이번 변경이 참조한 decision·lesson과 최종 구현·검증 근거가 일치하는지 확인한다. 승인되지 않은 commit·push·merge 권한을 추가하지 않는다.

## 상태와 근거

- decision의 `accepted`는 선택의 확정이고 lesson의 `active`는 읽을 대상이다. 어느 상태도 구현 완료·검증 통과·머지를 뜻하지 않는다.
- 기록의 선택 필드 `source_pr`는 관련 PR URL, `evidence_ref`는 실제 검증·대조 결과가 남은 PR 본문·댓글·리뷰·검사 결과 URL이다. 링크가 있다고 현재 HEAD에 대한 증거가 되는 것은 아니다 → 해당 결과의 SHA와 검증 범위를 읽는다.
- decision의 `implemented_in`과 lesson의 `promoted_to`는 실제 지침·검사 경로다. 일반 수정 경로와 검사·명령·결과·실패·미검증 범위는 본문 근거에 남긴다. 경험의 원인 확인과 해결책 반영·검증을 분리한다.
- 반영 결과는 `반영`, `부분 반영`, `미반영`, `반영 대상 없음`으로 보고하고, 검증 결과는 별도로 `통과`, `실패`, `미실행`과 실제 흐름 미검증 범위를 보고한다. 모든 lesson에 수정 구현을 요구하지 않는다. 조사로 확인한 원인이나 의도적으로 남긴 제한도 교훈이 될 수 있다.
- 문서·작업 지침 결정은 파일 내용·링크·절차의 일치로 대조한다. 런타임 코드·검사 강제·실제 에이전트 준수까지 확인했다고 확대하지 않는다.

## 마무리 절차

1. 이번 PR에서 추가·변경한 기록과, 영향 경로·조건이 맞는 기존 참조 기록을 고른다. 전체 저장소 기록을 일괄 재검증하지 않는다. 관련 기록이 없으면 없다고 적는다.
2. 실제 PR의 base와 head, 확인 시점의 head SHA를 읽고 최종 diff·구현·기록을 대조한다. 바뀐 방향·범위·예외·적용 조건을 기록에도 반영한다. 이전 결정의 이유를 지우거나 관련 없는 결정을 바꾸지 않는다.
3. 대상 경로의 필요한 검사를 실행해 명령·종료 코드·실패·미검증을 남긴다. 부분 반영·미반영은 남은 범위와 담당자의 허용 여부를 명시한다. 의도한 구현과 실제 코드가 다르면 완료라고 보고하지 않는다.
4. 기록 수정까지 끝낸 뒤 최종 commit·push가 승인된 범위에서 끝나면 최신 PR head SHA를 다시 읽고 대조 결과를 PR에 남긴다. 기록 파일에 자신의 최종 commit SHA를 넣기 위한 반복 커밋은 만들지 않는다. 기록에는 원천 PR과 근거 위치를 연결하고 정확한 최종 SHA는 PR의 결과에 둔다.
5. 이후 관련 코드·기록·base가 바뀌거나 rebase되면 기존 최종 확인을 현재 상태의 증거로 쓰지 않는다 → 최신 head에서 대조하고 영향받는 검사를 다시 실행한다. 다른 변경이라 기존 증거를 재사용한다면 영향이 없다는 diff 근거와 범위를 밝힌다.
6. 머지 직전 확인 담당자는 결과의 SHA가 현재 PR head와 같은지, 반영·검증의 미해결 사항이 처리됐는지 읽는다. 허용된 부분 반영은 남은 조건과 근거를 확인한다. 자동 CI 게이트는 아직 없으며 머지는 별도 권한이다.

## PR에 남길 형식

관련 기록이 있는 PR에서는 다음 정보만 필요한 만큼 남긴다. 여러 기록은 항목별로 구분한다.

```text
기록 대조 기준: PR #번호 / base / 최종 head SHA
기록: decision 또는 lesson 링크 / 적용 조건
반영: 반영·부분 반영·미반영·반영 대상 없음 / 실제 경로 / 남은 범위
검증: 명령 / 종료 코드 / 실패 / 미실행·실제 흐름 미검증
미해결: 허용 예외와 확인 근거 또는 필요한 후속 판단
```

## 계획과 후속 조회

- 계획에서 관련 확정 결정과 lesson을 읽을 때 합의·경험의 범위와 실제 반영·검증 범위를 구분한다. 확인한 revision과 현재 코드를 비교하고, 오래된 날짜나 머지 여부만으로 현재 유효성을 주장하지 않는다.
- appendix에는 사용한 기록과 실제 대조·검증 근거를 연결한다. 검증 링크가 없거나 읽지 못했으면 그 한계를 밝힌다.
- 머지 후 원천 PR에서 merge 여부·commit을 확인할 수 있다. merge 상태는 선택의 타당성·검사 성공·현재 코드의 일치를 대신하지 않는다.
