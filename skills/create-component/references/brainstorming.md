# Phase 0 Pre: 요구사항 Brainstorming

컴포넌트를 만들기 전에 사용자와 **5개 영역**을 합의한다. 합의 없이 Phase 0(아키텍처 분석)으로 넘어가지 않는다.

이 단계가 빠지면 다음 통증이 누적된다:
- 구현 후에 "사실 이게 필요한 게 아니었다"는 재작업
- 엣지케이스가 시나리오에 없어 비제어/접근성/모바일에서 깨짐
- 외부 레퍼런스를 임의로 골라 SEED 패턴과 충돌
- 토큰을 임의 생성해 rootage가 비대해짐

---

## 진행 방식 (Incremental)

5개 영역을 **순서대로, 한 영역씩** 다룬다. 한 영역에서 다음 패턴을 반복:

```text
한 영역에서:
  질문(한 번에 하나, 객관식 우선)
    ↓
  사용자 응답
    ↓
  "이렇게 이해했어, 맞아?" 짧은 확인
    ↓
  보강 질문 (모호한 경우)
    ↓
  영역 합의 ✅
    ↓ (다음 영역)
```

마지막에 5개 영역을 종합한 합의 요약을 한 번 더 보여주고 사용자의 **최종 컨펌**을 받는다 (게이트).

### 안티 패턴

- ❌ "이건 너무 간단해서 brainstorming 필요 없다" — 모든 컴포넌트가 이 단계를 거친다. 단순한 컴포넌트일수록 합의가 빠를 뿐.
- ❌ 5개 영역을 한 번에 다 묻기 — 사용자가 압도된다. 영역별로 incremental.
- ❌ 사용자의 모호한 답에 추측 덧붙이기 — 모호하면 다시 좁혀 묻는다.

### Red Flags (사용자가 이렇게 말하면 멈추고 다시 확인)

| 사용자 시그널 | 의미 | 다음 행동 |
|--------------|------|----------|
| "그냥 알아서 해줘" | 요구사항이 본인도 명확하지 않음 | 객관식 후보를 만들어 좁히기 |
| "Base UI처럼 만들어줘" | 외부 라이브러리를 그대로 베끼라는 신호 | SEED 패턴과 충돌 영역을 먼저 확인 |
| "엣지케이스는 나중에" | 가장 흔한 후회의 원인 | 코드 진입 전에 한 번에 합의해야 한다고 설명 |
| "기존 X 컴포넌트랑 비슷한데..." | 기존 확장일 가능성 | §2 기존과의 관계로 분기 |
| "토큰은 적당히..." | 토큰 임의 생성의 신호 | rootage 책임자(Ask first) 확인 필요 |

## 시각 동반자 (옵션)

컴포넌트는 시각 작업이다. 다음 중 가능한 자료가 있으면 brainstorming 중 활용:

- Figma 시안 링크
- 외부 라이브러리(Base UI / Radix / Chakra / shadcn)의 데모 페이지 링크
- 유사 SEED 컴포넌트의 Storybook URL
- 사용자가 가진 mockup / 스크린샷

시각 자료가 있으면 §3 엣지케이스(상태별 시각화)와 §5 외부 레퍼런스 비교에서 결정이 훨씬 빨라진다. 진입 시 시각 자료 유무를 한 번 묻는다:

> "이 컴포넌트에 대한 Figma 시안이나 mockup이 있어? 또는 따라가고 싶은 외부 라이브러리 데모?"

없으면 텍스트만으로 진행한다.

## 1. Purpose — 왜 / 누가 / 어떤 사용 사례인가

이 컴포넌트가 왜 존재해야 하는지 사용자와 합의한다.

### 질문 가이드 (한 번에 하나씩)
1. 어떤 사용자(개발자 / 디자이너 / PM)가 어떤 화면·플로우에서 쓸 것인가?
2. 이미 비슷한 게 SEED나 당근 프로덕트에 있는가? 있다면 왜 그것을 쓰지 않는가?
3. 이 컴포넌트가 해결하는 1차 문제는 무엇인가? (한 문장으로)
4. 1차 문제가 풀리지 않으면 사용자가 어떻게 우회하고 있는가?

### 합의 확인
"이 컴포넌트는 _[사용자]_가 _[화면·플로우]_에서 _[문제]_를 풀기 위해 쓰는 거야, 맞지?"

### 영역 게이트
**금지**: "유용할 것 같아서" / "있으면 좋을 것 같아서"만으로 진행하지 않는다. 구체적 사용 사례가 적어도 1개 있어야 §2로 진입.

## 2. 기존과의 관계 — 신규 / 확장 / 대체

새 컴포넌트가 SEED 안에서 어떤 위치를 차지하는지 확인한다.

### 선택지 (객관식)

| 유형 | 의미 | 추가 합의 사항 |
|------|------|---------------|
| **신규** | SEED에 없는 새 컴포넌트 | 가장 유사한 SEED 컴포넌트, 외부 레퍼런스 |
| **기존 확장** | 기존 컴포넌트에 새 variant/slot 추가 | 기존 API 호환성, breaking change 여부 |
| **대체** | 기존 컴포넌트의 deprecation 대상 | 마이그레이션 경로, deprecation 일정 |

### 유사 컴포넌트 매트릭스
패턴 참조용으로 다음 4개 경로를 함께 합의:

- Headless ref: `packages/react-headless/<name>` 중 어느 것?
- Styled ref: `packages/react/src/components/<Name>` 중 어느 것?
- Snippet ref: `docs/registry/ui/<name>.tsx` 중 어느 것? (or N/A)
- Rootage ref: `packages/rootage/components/<name>.yaml` 중 어느 것?

### 합의 확인
"_[유형]_으로 가고, 패턴 참조는 Headless=_[X]_, Styled=_[Y]_, Snippet=_[Z]_, Rootage=_[W]_야, 맞지?"

## 3. 엣지케이스 시나리오 — 깨질 수 있는 모든 곳

구현 후 발견되는 통증의 가장 흔한 원인. 시작 전에 모두 합의한다.

### 필수 합의 영역 (객관식, 영역마다 O/X 또는 짧은 응답)

| 영역 | 합의할 항목 |
|------|------------|
| 상태 | 로딩 / 에러 / 빈 상태 / 비활성 / 읽기 전용 |
| 제어 | 제어/비제어 모두 지원? defaultValue 동작? `useControllableState` 사용? |
| 키보드 | Space/Enter / Arrow / Home/End / Escape / Tab — 각 동작 정의 |
| 스크린리더 | ARIA role / aria-* / live region 필요한가? |
| 모바일 | 터치 타겟 크기 (≥24px, 권장 ≥44px), engaged 상태(hover 대신), 스크롤 동작 |
| 폼 통합 | Field 컨텍스트 통합? 숨겨진 native input 필요? |
| 다국어/RTL | RTL 환경에서 방향이 바뀌어야 하는가? |
| 폰트 스케일링 | t1~t10 어디까지 지원? overflow 동작? |

### 진행 패턴 (이 섹션은 영역 안에서도 incremental)

각 항목을 한 묶음씩 던지고 사용자 응답 받기:

> "상태 시나리오 먼저 — 로딩 / 에러 / 빈 상태 / 비활성 / 읽기 전용 중 이 컴포넌트가 다뤄야 하는 건? (필요 없으면 X)"

> "다음으로 제어 — 제어/비제어 모두? 또는 한쪽만? (대부분 SEED는 `useControllableState`로 둘 다 지원)"

이런 식으로 5-8번 짧은 질문을 던진다.

### 영역 게이트
**금지**: "기본 케이스만 먼저" / "엣지케이스는 나중에" — 코드를 쓰기 전에 한 번에 합의한다.

## 4. 토큰 의존성 — 신규 / 기존

`packages/rootage/`의 토큰 정의가 새 컴포넌트를 지원하는지 확인.

### 합의할 것 (객관식)

1. **기존 토큰으로 충분?** (대부분의 경우 Yes)
2. **새 토큰이 필요하다면:**
   - 어느 collection? (color / spacing / typography / radius / shadow / motion)
   - 누가 정의? — 2-3 접근법 비교:

     | 접근법 | 언제 | 트레이드오프 |
     |--------|------|------------|
     | Figma 동기화 기다림 | 디자인 시스템 토큰을 Figma가 먼저 정의해야 할 때 | 안전하지만 느림 |
     | 임시 추가 후 동기화 | 토큰 형태가 명확하고 Figma 정의가 뒤따를 예정일 때 | 빠르지만 동기화 리스크 |
     | 컴포넌트별 vars만 사용 | 토큰 자체는 기존, 컴포넌트 vars 자동 생성 | 가장 안전, 가장 빠름 |

3. **토큰 이름 컨벤션** (예: `$color.bg.brand.subtle`, `$spacing.gap.large`)

### 합의 확인
"토큰은 _[기존 사용 / 새 토큰 N개 추가]_, 추가 방식은 _[Figma 기다림 / 임시 추가 / 컴포넌트별 vars]_, 맞지?"

### 영역 게이트
새 토큰 추가는 `Ask first` 영역(AGENTS.md §Boundaries)이므로 사용자 확인 필수.

## 5. 외부 레퍼런스 우선순위 — 어느 라이브러리부터?

외부 라이브러리는 영감이지 복사 대상이 아니다. **SEED 아키텍처가 항상 최우선.** 하지만 어느 라이브러리의 어떤 패턴을 우선 참고할지는 합의가 필요하다.

### 라이브러리별 우선 참고 영역

| 라이브러리 | 우선 참고 영역 | 언제 우선? |
|-----------|---------------|----------|
| **Base UI React** | headless 훅 API, controlled/uncontrolled, 접근성 구현 | 카테고리 C/D 신규 |
| **Radix Primitives** | compound 구조, slot 분리 기준, 포커스 관리 | compound 설계 시 |
| **Chakra UI** | prop 인터페이스, variant 체계, 네이밍 | prop 설계 시 |
| **shadcn/ui** | snippet/registry 패턴, 사용자 API 형태 | snippet 설계 시 |

### 2-3 접근법 비교 패턴 (인터페이스가 갈릴 때)

같은 결정 영역에서 라이브러리들이 다르게 답하는 경우, 다음 3가지 후보를 정리해서 사용자에게 선택받는다:

> **예: Accordion의 `value` 인터페이스**
>
> - (A) Radix 방식: `<Accordion type="single|multiple" value=...>`
> - (B) Base UI 방식: `<Accordion multiple value=...>` (boolean capability)
> - (C) SEED 기존 패턴: `useControllableState`로 single/multiple을 별도 컴포넌트로 분리
>
> 각각의 장단점은? SEED에서 가장 가까운 선례는?

후보 3개를 만들기 어렵거나 한 라이브러리가 명확히 우월하면 1순위 룰을 따른다.

### 상세
**라이브러리 우선순위 룰 + 차용 vs 거부 결정 트리**: `references/external-references.md`

### 합의 확인
"1순위는 _[라이브러리]_의 _[영역]_, 2순위는 _[라이브러리]_의 _[영역]_, SEED 패턴과 충돌 시 _[기준]_으로 결정해, 맞지?"

## 산출물 — 합의 요약 템플릿

Phase 0 Pre가 끝나면 다음 템플릿을 채워 메모(또는 PR description 초안)로 남긴다. Phase 0의 입력이 된다.

```markdown
## 컴포넌트: <Name>

### Purpose
- 1차 사용자/사용 사례: <한 문장>
- 1차 문제: <한 문장>
- 현재 우회 방법: <한 문장>

### 관계
- 유형: 신규 / 확장 / 대체
- 가장 유사한 SEED 컴포넌트: <name>
- Headless ref: <path>
- Styled ref: <path>
- Snippet ref: <path or N/A>
- Rootage ref: <path>

### 엣지케이스 합의
- 상태: 로딩 [O/X] / 에러 [O/X] / 빈 [O/X] / 비활성 [O/X] / 읽기전용 [O/X]
- 제어: controlled [O/X] / uncontrolled [O/X] / useControllableState [O/X]
- 키보드: <키별 동작>
- 스크린리더: role=<...>, aria-<...>
- 모바일: 터치타겟 ≥ <Npx>, engaged 상태 [O/X]
- 폼: Field 통합 [O/X] / hidden native input [O/X]
- RTL [O/X] / 폰트스케일 t1~t10 [O/X]

### 토큰
- 기존 토큰으로 충분: [Yes/No]
- 신규 토큰: <목록 또는 N/A>
- 추가 방식: Figma 기다림 / 임시 추가 / 컴포넌트별 vars

### 외부 레퍼런스 우선순위
- 1순위: <라이브러리, 참고 영역>
- 2순위: <라이브러리, 참고 영역>
- SEED 패턴과 충돌 시: <어떻게 결정할지>
```

## 🔒 최종 게이트

5개 영역 모두 합의된 후, **합의 요약을 사용자에게 한 번에 보여주고** 명시적 컨펌을 받는다:

> "위 요약대로 진행할까? 빠진 거나 수정할 거 있어?"

사용자가 **"이대로 진행"**(또는 명확한 동의)이라고 답해야 Phase 0(아키텍처 분석) 진입.

컨펌이 모호하거나("음... 일단 가보자" 등) 추가 의견이 있으면 해당 영역만 따로 다시 좁혀 묻는다. 추측해서 채우지 않는다.
