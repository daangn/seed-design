# 요구사항 탐색

새 컴포넌트의 목적이나 공개 계약에 중요한 빈칸이 있을 때 사용한다. 사용자가 이미 구체적으로 정한 내용은 다시 묻지 않는다. 구현 방향을 바꿀 수 있는 항목만 확인한다.

이 단계가 빠지면 다음 통증이 누적된다:
- 구현 후에 "사실 이게 필요한 게 아니었다"는 재작업
- 엣지케이스가 시나리오에 없어 비제어/접근성/모바일에서 깨짐
- 외부 레퍼런스를 임의로 골라 SEED 패턴과 충돌
- 토큰을 임의 생성해 rootage가 비대해짐

---

## 진행 방식

구현 방향이나 공개 계약을 실제로 바꿀 수 있는 빈칸만 적는다. 기존 컴포넌트와 사용자 요청에서 합리적으로 결정할 수 있으면 그 근거를 사용해 진행하고, 선택에 따라 사용자 결과·저장소 경계·외부 변경이 달라지는 항목만 질문한다.

1. 이미 확정된 요구사항과 가까운 구현을 읽어 결정 가능한 항목을 채운다.
2. 남은 결정이 사용자 결과나 새 패키지·토큰·외부 의존성·CI 범위를 바꾸는지 구분한다.
3. 전자 중 되돌리기 어려운 선택만 짧은 후보와 영향으로 질문한다. 이미 요청된 공개 API의 세부 naming·구현 순서는 기존 패턴을 따른다.
4. 답을 받은 항목만 기록하고 구현으로 이어간다. 읽기 전용 분석과 되돌릴 수 있는 구현 세부에는 승인 단계를 만들지 않는다.

### 안티 패턴

- 구현을 바꾸지 않는 질문까지 형식적으로 반복하지 않는다.
- 여러 영역을 한 번에 묻지 않는다.
- 모호한 답에 추측을 덧붙이지 않는다. 결정이 필요한 부분만 다시 좁혀 묻는다.

### 판단 신호

| 사용자 시그널 | 처리 |
|--------------|------|
| "그냥 알아서 해줘" | 가까운 기존 패턴과 명시 요구로 합리적인 기본값을 정하고, 저장소 경계가 바뀌는 선택만 묻는다. |
| "Base UI처럼 만들어줘" | 복사하지 않고 SEED 패턴과 충돌하는 공개 계약만 확인한다. |
| "엣지케이스는 나중에" | 실제 요청과 가까운 기존 시나리오에서 필요한 경계만 구현·검증한다. |
| "기존 X 컴포넌트랑 비슷한데..." | 해당 컴포넌트를 먼저 읽고 확장·대체 여부를 판단한다. |
| "토큰은 적당히..." | 기존 토큰을 우선하고 새 토큰이 필요할 때만 boundary 확인을 한다. |

## 시각 자료 (선택)

컴포넌트 작업에 영향을 줄 시각 자료가 있을 때만 사용한다.

- Figma 시안 링크
- 외부 라이브러리 데모 페이지 링크
- 유사 SEED 컴포넌트의 Storybook URL
- 사용자가 가진 mockup·스크린샷

자료의 유무가 구현 결과를 바꿀 때만 한 번 질문한다. 자료가 없거나 결과에 영향을 주지 않으면 텍스트와 기존 패턴으로 진행한다.

## 1. Purpose — 왜 / 누가 / 어떤 사용 사례인가

이 컴포넌트가 왜 존재해야 하는지 사용자와 합의한다.

### 질문 가이드 (한 번에 하나씩)
1. 어떤 사용자(개발자 / 디자이너 / PM)가 어떤 화면·플로우에서 쓸 것인가?
2. 이미 비슷한 게 SEED나 당근 프로덕트에 있는가? 있다면 왜 그것을 쓰지 않는가?
3. 이 컴포넌트가 해결하는 1차 문제는 무엇인가? (한 문장으로)
4. 1차 문제가 풀리지 않으면 사용자가 어떻게 우회하고 있는가?

### 합의 확인
"이 컴포넌트는 _[사용자]_가 _[화면·플로우]_에서 _[문제]_를 풀기 위해 쓰는 거야, 맞지?"

### 확인 기준
**금지**: "유용할 것 같아서" / "있으면 좋을 것 같아서"만으로 진행하지 않는다. 구체적 사용 사례가 적어도 1개 있어야 §2로 진입.

## 2. 기존과의 관계 — 신규 / 확장 / 대체

새 컴포넌트가 SEED 안에서 어떤 위치를 차지하는지 확인한다.

### 선택지 (객관식)

| 유형 | 의미 | 추가 합의 사항 |
|------|------|---------------|
| **신규** | SEED에 없는 새 컴포넌트 | 가장 유사한 SEED 컴포넌트, 외부 레퍼런스 |
| **기존 확장** | 기존 컴포넌트에 새 variant/slot 추가 | 기존 API 호환성, breaking change 여부 |
| **대체** | 기존 컴포넌트의 deprecation 대상 | 마이그레이션 경로, deprecation 일정 |

### 유사 컴포넌트 매트릭스
패턴 참조용으로 target platform에 맞는 경로를 함께 합의:

- Headless ref:
  - React: `packages/react-headless/<name>` 중 어느 것?
  - Lynx: `packages/lynx-react/src/hooks`, 컴포넌트 내부 hook/context, 기존 외부 primitive 중 어느 것?
- Styled ref:
  - React: `packages/react/src/components/<Name>` 중 어느 것?
  - Lynx: `packages/lynx-react/src/components/<Name>` 중 어느 것?
- Snippet ref:
  - React: `docs/registry/react/ui/<name>.tsx` 중 어느 것? (or N/A)
  - Lynx: `docs/registry/lynx/ui/<name>.tsx` 중 어느 것? (or N/A)
- Rootage ref: `packages/rootage/components/<name>.yaml` 중 어느 것?

### 합의 확인
"_[유형]_으로 가고, Platform=_[react/lynx/cross-platform]_, 패턴 참조는 Headless=_[X]_, Styled=_[Y]_, Snippet=_[Z]_, Rootage=_[W]_야, 맞지?"

## 3. 엣지케이스 시나리오

상태·입력·접근성 계약을 새로 만들거나 바꿀 때만 적용한다. 기존 동작을 건드리지 않는 작은 변경에 모든 항목의 합의를 요구하지 않는다. 관련된 경우에는 가까운 기존 컴포넌트와 플랫폼 계약을 근거로 필요한 경계를 정하고, 새 토큰·패키지·외부 의존성처럼 boundary에 해당하는 선택만 사용자에게 확인한다.

| 영역 | 확인이 필요한 경우 |
|------|-------------------|
| 상태 | loading, error, empty, disabled, read-only 결과를 새로 지원하거나 변경할 때 |
| 제어 | controlled/uncontrolled 또는 기본값 계약을 추가·변경할 때 |
| 입력·접근성 | React 키보드·focus 또는 Lynx 터치·제스처·`accessibility-*` 계약을 바꿀 때 |
| 폼 통합 | Field·native input 또는 Lynx 런타임 지원 여부가 사용자 결과에 영향을 줄 때 |
| 터치·폰트 스케일링 | 해당 화면의 target size, overflow, layout 결과를 바꿀 때 |

### 진행 패턴

남은 결정이 사용자 결과나 저장소 경계를 바꿀 때만 해당 영역을 선택해 짧게 질문한다. 질문 수를 정하지 않고, 가까운 기존 컴포넌트와 명시된 요구사항으로 결정 가능한 항목은 바로 채운다.

예:

> "상태 — 로딩 / 에러 / 빈 상태 / 비활성 / 읽기 전용 중 새로 다뤄야 하는 결과가 있어?"

> "제어 — controlled와 uncontrolled 중 어떤 계약이 필요한가? 기존 컴포넌트가 양쪽을 지원하면 그 패턴을 따른다."

### 확인 기준

필요한 상태·입력·접근성 경계는 구현 전에 확정한다. 작은 변경에 관련 없는 엣지케이스 합의나 질문을 추가하지 않는다.

## 4. 토큰 의존성 — 신규 / 기존

`packages/rootage/`의 토큰 정의가 새 컴포넌트를 지원하는지 확인.
### 확인할 것 (새 토큰이 필요한 경우)

기존 Rootage 토큰으로 표현할 수 있으면 그대로 사용한다. 새 토큰이 필요한 경우에만 collection, 정의 경로와 이름을 정리하고 `AGENTS.md`의 경계에 따라 사용자 확인을 받는다.

1. 어느 collection인가? (`color`, `spacing`, `typography`, `radius`, `shadow`, `motion`)
2. Figma 동기화가 필요한가, 컴포넌트별 vars로 충분한가?
3. 기존 토큰과 일관된 이름인가? (예: `$color.bg.brand.subtle`, `$spacing.gap.large`)

### 확인 기준

새 토큰 추가는 `AGENTS.md`의 사전 확인 대상이다. 기존 토큰 선택이나 되돌릴 수 있는 이름 정리는 별도 승인 없이 기존 패턴을 따른다.

## 5. 외부 레퍼런스 우선순위 — 어느 라이브러리부터?

외부 라이브러리는 영감이지 복사 대상이 아니다. 기존 SEED 패턴으로 결정할 수 있으면 외부 비교를 생략한다. 인터페이스 선택이 사용자 결과나 공개 계약을 바꾸고 기존 선례가 충분하지 않을 때만 비교한다.

### 라이브러리별 우선 참고 영역

| 라이브러리 | 우선 참고 영역 | 언제 우선? |
|-----------|---------------|----------|
| **Base UI React** | headless 훅 API, controlled/uncontrolled, 접근성 구현 | 카테고리 C/D 신규 |
| **Radix Primitives** | compound 구조, slot 분리 기준, 포커스 관리 | compound 설계 시 |
| **Chakra UI** | prop 인터페이스, variant 체계, 네이밍 | prop 설계 시 |
| **shadcn/ui** | snippet/registry 패턴, 사용자 API 형태 | snippet 설계 시 |

### 접근법 비교 (인터페이스가 갈릴 때)

같은 결정 영역에서 기존 SEED 패턴과 외부 라이브러리의 답이 갈리고 결과가 달라질 때만 후보와 장단점을 정리한다. 결과를 바꾸지 않는 참고나 단순 구현 세부에는 후보 선택을 요구하지 않는다.

> **예: Accordion의 `value` 인터페이스**
>
> - (A) Radix 방식: `<Accordion type="single|multiple" value=...>`
> - (B) Base UI 방식: `<Accordion multiple value=...>` (boolean capability)
> - (C) SEED 기존 패턴: `useControllableState`로 single/multiple을 별도 컴포넌트로 분리
>
> 각 선택의 장단점과 SEED에서 가장 가까운 선례를 기록한다.

후보를 비교할 때는 사용자 결과와 유지보수 비용이 달라지는 선택만 남긴다. 결과를 바꾸지 않는 참고나 단순 구현 세부는 가장 가까운 기존 패턴을 따른다.

### 상세
**라이브러리 우선순위 룰 + 차용 vs 거부 결정 트리**: [external-references.md](external-references.md)

### 결정 기록 (필요한 경우)

되돌리기 어려운 공개 계약이나 저장소 경계만 근거와 함께 사용자에게 확인한다.

## 합의 요약 템플릿

여러 레이어나 공개 API를 새로 결정했다면 다음 템플릿에서 해당하는 항목만 채운다. 단순 변경에 빈 항목을 억지로 만들지 않는다.

```markdown
## 컴포넌트: <Name>

### Platform
- Target: react / lynx / cross-platform
- 이유: <요청/경로/import/docs 근거>
- Lynx support delta: <웹 대비 차이 또는 N/A>
- Headless ownership: React headless / Lynx hook·context / 기존 외부 Lynx primitive / 없음
- Docs/registry target: <docs/content/... + docs/registry/... 경로>

### Purpose
- 1차 사용자/사용 사례: <한 문장>
- 1차 문제: <한 문장>
- 현재 우회 방법: <한 문장>

### 관계
- 유형: 신규 / 확장 / 대체
- 가장 유사한 SEED 컴포넌트: <name>
- Headless ref: <path>
- Styled ref: <path>
- Snippet ref: <path or N/A>
- Rootage ref: <path>

### 엣지케이스 합의
- 상태: 로딩 [O/X] / 에러 [O/X] / 빈 [O/X] / 비활성 [O/X] / 읽기전용 [O/X]
- 제어: controlled [O/X] / uncontrolled [O/X] / useControllableState [O/X]
- React 입력·접근성: <키보드·focus 동작>, role=<...>, aria-<...>, native input [O/X]
- Lynx 입력·접근성: <터치·제스처 동작>, accessibility-<...>, 플랫폼 제약 <...>
- 터치 타겟 ≥ <Npx>, engaged 상태 [O/X]
- 폼: React Field 통합 [O/X] / Lynx 런타임 지원 [O/X]
- RTL [O/X] / 폰트스케일 t1~t10 [O/X]

### 토큰
- 기존 토큰으로 충분: [Yes/No]
- 신규 토큰: <목록 또는 N/A>
- 추가 방식: Figma 기다림 / 임시 추가 / 컴포넌트별 vars

### 외부 레퍼런스 우선순위
- 1순위: <라이브러리, 참고 영역>
- 2순위: <라이브러리, 참고 영역>
- SEED 패턴과 충돌 시: <어떻게 결정할지>
```

## 사용자 확인이 필요한 경우

새 패키지, 새 토큰, 외부 의존성, CI 변경처럼 저장소 경계나 외부 변경을 추가해야 할 때만 근거와 영향을 보여주고 확인받는다. 요청한 공개 API의 구현 세부, 기존 패턴으로 결정 가능한 선택, 되돌릴 수 있는 문서·코드 구성에는 별도 확인을 요구하지 않는다.
