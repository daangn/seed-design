# 막힘 처리 규칙

컴포넌트 작업이 막히면 이 순서를 따른다.

1. 아래 [차단점](#즉시-중단하고-보고할-차단점) 중 하나에 해당하는지 본다. 해당하면 그 작업을 멈춘다. 해당하지 않으면 원인을 더 조사하고 원천을 고친다.
2. [통증 메모](#통증-메모-템플릿)를 쓴다: 무엇이 막혔는지, 무엇을 시도했는지, 어느 차단점인지.
3. 사용자에게 메모와 선택지를 바로 보고한다.
4. 사용자 결정대로 재시도하거나 합의한 우회 경로로 진행한다.

토큰·recipe·headless·snippet이 서로 강하게 연결돼 있어서, 한 컴포넌트의 mock·생략은 그 컴포넌트를 패턴 참조로 삼는 다음 작업에 그대로 복제된다.

## 막혔을 때 절대 하지 않는 것

- 의도와 다른 동작으로 일단 통과시키지 않는다 → 원천을 고치거나 사용자에게 보고한다.
- mock 데이터·mock 컴포넌트로 실제 구현을 대신하지 않는다(테스트 코드 안의 mock은 제외) → 없는 의존성은 차단점으로 보고한다.
- `as any`·`as unknown`으로 타입을 우회하지 않는다(루트 `TECH.md`「TypeScript」) → 타입 원천을 고치거나 타입 문제를 보고한다.
- `it.skip`, `describe.skip`, 테스트 삭제로 실패를 숨기지 않는다 → 실패를 "자동 검증 실패" 차단점으로 보고한다.
- "나중에 고치자" 주석을 남기고 진행하지 않는다 → 지금 고치거나 통증 메모에 남겨 보고한다.
- 바꾼 패턴을 일부 컴포넌트에만 적용하지 않는다 → 같은 패턴을 쓰는 기존 컴포넌트를 모두 갱신하거나 적용 범위를 사용자와 정한다.

## 즉시 중단하고 보고할 차단점

다음은 임의로 진행하지 않고 사용자 결정을 받는다.

- 의존성 불안정 → 의존하는 컴포넌트 API가 `dev` 브랜치에 머지되지 않았다.
- 토큰 누락 → 필요한 토큰이 Rootage에 없어 새 토큰을 추가해야 한다.
- ARIA 패턴 충돌 → APG 패턴이 모호하거나 SEED 기존 패턴(`useControllableState`, namespace 등)과 충돌한다.
- 외부 레퍼런스 갈림 → Base UI, Radix, Chakra, shadcn의 인터페이스가 다르고 [라이브러리 우선순위 룰](external-references.md#라이브러리-우선순위-룰)로도 정해지지 않는다.
- 자동 검증 실패 → 생성 명령, 경로별 테스트, `bun packages:build`, `bun docs:test`, 플랫폼별 빌드 중 하나가 실패하고 변경 범위 안에서 원인을 고쳐 해결할 수 없다.
- 시각 회귀 → Storybook, `examples/stackflow-spa`, `examples/lynx-spa`에서 기존 컴포넌트의 시각 결과가 달라졌다.

## 통증 메모 템플릿

세션 메모나 PR 본문처럼 사용자와 공유되는 곳에 짧게 남긴다.

```markdown
### 통증: <한 문장 요약>
- 작업 위치: 요구사항 / 구조 결정 / 구현 레이어 / 검증
- 시도한 것: <bullet>
- 차단점 분류: 의존성 / 토큰 / ARIA / 외부 레퍼런스 / 자동 검증 / Visual
- 사용자 결정: <받은 결정 또는 보류>
- 결과: 재시도 성공 / 우회 경로 / 보류
```

같은 차단점이 두 번 이상 반복되면 해당 reference나 가장 좁은 경로의 `AGENTS.md`에 규칙을 추가하자고 사용자에게 제안한다.
