# .agents/decisions

사람이 선택한 방향과 그 이유·적용 조건을 보존하는 저장소 내부 결정 기록이다. 폴더는 자동 로딩이나 검사 강제를 제공하지 않으며, 읽기·기록은 아래 절차를 따른다.

## 검증

- 필수 필드·고유 ID·scope·상태·근거 링크를 확인한다. description만으로 어떤 선택에서 읽고 언제 제외할지 설명할 수 있어야 한다.
- `accepted`에는 사람이 확정한 근거와 날짜가 있어야 한다. `superseded_by`의 대상이 존재하고 대체 관계가 순환하지 않는지 확인한다.
- 관련 결정과 현재 적용 경로의 규칙을 비교한다. 충돌을 새 파일로 숨기지 않고 적용 조건 또는 대체 관계를 명시한다.
- `git diff --check -- AGENTS.md .agents/decisions`와 내용·링크·형식을 확인한다. 새 파일도 직접 검토한다. 문서 변경에 제품 테스트·빌드를 실행하지 않는다.

## 규칙

### 기록 범위

- 여러 대안 사이에서 선택했고 후속 작업이 그 이유를 알아야 하는 공개 계약·도메인·패키지 경계·품질 기준·공유 작업 절차를 기록한다. 단순 구현 세부 사항과 모든 PR을 결정으로 남기지는 않는다.
- lesson은 경험에서 확인한 원인·조건·다음 행동이고, decision은 선택·대안·비용·합의다. 관련 lesson은 링크하며 같은 본문을 복사하지 않는다.
- 에이전트가 초안을 작성할 수 있지만 스스로 팀 합의를 선언하지 않는다 → 미확정 선택은 `proposed`로 남기거나 현재 PR의 논의로 둔다. 사용자 명시 요청 또는 해당 영역 담당자의 확인을 근거로 `accepted`로 기록한다. 저장소 전체 합의로 확대하지 않는다.
- 기존 결정을 일괄 이관하거나 코드에서 의도를 추측해 확정하지 않는다 → 이번 작업에서 필요한 결정만 원천과 사람의 확인을 갖춰 기록한다.
- 결정은 사용자 요청과 현재 경로 규칙 안에서 적용한다. 적용 범위 내 충돌이나 예외가 필요하면 계획에 근거·영향·대안을 드러내고 담당자의 판단을 받는다. 다른 범위의 결정까지 뒤집거나 오래된 기록을 무조건 우선하지 않는다.

### 형식과 상태

- `entries/<id>.md`에 결정 하나를 둔다. 별도 수동 인덱스를 만들지 않고 frontmatter를 조회 원천으로 삼는다.
- 필수 필드는 `id`, `description`, `scope`, `status`다. ID는 파일명과 같은 고유 kebab-case다. scope는 저장소 상대 경로 패턴의 배열이며 공통 기록은 `["**"]`다.
- description은 2–3문장으로 판단할 선택·조건·제외 조건·얻을 근거를 설명한다. 조회를 위해 필드는 한 줄로 쓰고 `id`·`status`는 따옴표 없이, 배열은 `["값"]`으로 쓴다. `: ` 등이 있는 설명은 문자열 전체를 따옴표로 감싼다.
- `proposed`: 논의 중이며 계획을 강제하지 않는다. 관련 미해결 선택에 영향을 주면 계획에 표시한다.
- `accepted`: 확인된 적용 조건 안에서 계획의 기준으로 쓴다. `decided_at: "YYYY-MM-DD"`와 본문의 확정 근거를 남긴다. 담당자가 확인되면 `owner`에 역할 또는 계정을 적고, 모르면 만들지 말고 미정으로 표시한다.
- `superseded`: 확인된 새 결정으로 대체됐다. `superseded_by`에 새 결정 ID와 본문에 이유를 남긴다.
- `retired`: 더 이상 적용하지 않는다. 이유를 남기고 기본 조회에서 제외한다. 비활성 결정도 이력을 보존한다.
- 선택 필드 `related_decisions`는 결정 ID 배열, `related_learnings`는 lesson ID 배열, `implemented_in`은 실제 지침·검사 파일의 상대 경로 배열이다. 구현 연결은 검증 통과나 정책 확정 상태를 대신하지 않는다. 검사로 옮겨도 결정의 이유는 이 기록에 남긴다.
- 본문은 `## 결정과 적용 조건`, `## 배경·대안·비용`, `## 확정 근거와 재검토`로 쓴다. 허용 예외, 원천 PR·사용자 요청, 담당자, 재검토 조건을 적는다. PR 근거가 없으면 요청 날짜와 확인한 내용을 적고 링크를 지어내지 않는다.

## 작업 절차

### 조회와 계획

1. 작업 경로·키워드로 frontmatter를 조회한다. 공통 scope를 포함하고 status·scope·description의 조건이 맞는 `accepted` 본문만 읽는다. 관련 `proposed`는 미해결 판단에 필요할 때만 읽는다.
2. 관계 대상도 metadata부터 확인한다. 대체·폐기 기록을 찾으면 상태와 이동 경로를 확인하며 모든 본문을 재귀적으로 읽지는 않는다.
3. 계획에 이번 선택에 영향을 주는 결정 링크, 적용 조건, 일치 여부 또는 필요한 예외를 짧게 남긴다. 관련 결정이 없으면 없다고 표시하며 기록을 만들어 맞추지 않는다. 사소한 변경에 별도 보고를 강제하지 않는다.

아래 검색은 scope 자동 매칭이 아니다. 출력된 패턴과 description의 실제 조건을 판단한다. Bash가 없으면 Glob·Grep·Read로 같은 metadata만 조회하며 권한을 넓히지 않는다.

```bash
decision_query='공개 API|패키지|스킬'
rg --files --hidden .agents/decisions/entries -g '*.md' | sort |
while IFS= read -r decision_file; do
  decision_meta=$(awk '
    NR == 1 { if ($0 != "---") exit; next }
    /^---$/ { printf "%s", metadata; exit }
    { metadata = metadata $0 ORS }
  ' "$decision_file")
  printf '%s\n' "$decision_meta" | rg -q '^status: (accepted|proposed)$' || continue
  printf '%s\n' "$decision_meta" | rg -qi -e "$decision_query" -e '^scope: \["\*\*"\]$' || continue
  printf '\n%s\n%s\n' "$decision_file" "$decision_meta"
done
```

### 기록과 적용

1. 기록 전 비활성 항목을 포함해 중복·관련 결정을 조회한다. 같은 선택은 기존 기록을 보강하고, 선택이 바뀌면 새 기록과 대체 관계를 남긴다. 원래 근거를 덮어쓰지 않는다.
2. 작업 중 사람이 중요한 선택을 확정했으면 이유·대안·예외·근거를 작성한다. 확인되지 않은 추론은 확정 근거로 쓰지 않는다. 읽기 전용 계획·리뷰에서는 후보만 보고하고 파일을 쓰지 않는다.
3. 관련 lesson은 근거로 연결한다. 결정에 따른 실행 기준은 가장 좁은 AGENTS·Skill·타입·스키마·테스트·lint·CI 중 맞는 위치에 둔다. 문서 지침과 실행 검사를 구분한다.
4. 검사 추가는 별도 변경으로 적용 범위·정상 사례·위반·허용 예외·기존 위반·오탐을 확인하고 `implemented_in`에 실제 경로를 연결한다. 결정 기록만으로 새 의존성·설정·CI 변경 권한이 생기지 않는다.
5. 완료 응답에 추가·변경한 결정과 미확정 사항을 알린다. commit·push·PR은 루트 승인 범위를 따른다. lesson의 자동 커밋 예외를 결정 기록에 확대하지 않는다.
